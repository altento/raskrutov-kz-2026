# Raskrutov.kz — GitHub Single-Writer

Этот пакет делает GitHub-репозиторий общим источником состояния для двух Windows-ПК и вводит правило:

> одновременно правом изменения проекта обладает только один компьютер.

## Что происходит автоматически

При отправке промта в Cursor:

1. `beforeSubmitPrompt` делает Git preflight;
2. обновляет `origin`;
3. безопасно fast-forward обновляет чистый `main`, если он просто отстал;
4. атомарно создаёт remote lock `cursor-lock/site-write`;
5. если lock уже принадлежит другому ПК — сам промт блокируется.

Когда ответ агента завершён:

- если рабочее дерево чистое и ветка полностью передана в upstream, lock снимается;
- если остались локальные изменения или непереданные commit, lock сохраняется за этим ПК.

Git hooks отдельно блокируют `commit` и `push` без правильного lock.

## Почему lock нельзя одновременно получить на двух ПК

Создание remote lock использует Git `--force-with-lease=<ref>:` с пустым ожидаемым SHA.
Это означает: создать ref разрешено только если ref ещё не существует.

Даже если ПК1 и ПК2 попытаются получить lock почти одновременно, GitHub примет только одного владельца.

## Что это защищает

- Cursor Agent не должен запускать промт на втором ПК, пока первый удерживает lock.
- Commit/push на втором ПК блокируется versioned Git hooks.
- Локальные незавершённые изменения удерживают lock за текущим ПК.
- Устаревший `main` при чистом checkout автоматически fast-forward обновляется.

## Что это НЕ является

Это не механизм безопасности уровня разных GitHub-аккаунтов.

Оба ПК используют один GitHub identity, поэтому GitHub сам по себе не знает, с какого физического компьютера пришёл push.

Защита построена слоями:

1. Cursor `beforeSubmitPrompt`;
2. Cursor `preToolUse`;
3. versioned `pre-commit`;
4. versioned `pre-push`;
5. atomic remote lock.

Ручное редактирование файлов вне Cursor технически возможно, но commit/push без lock будет заблокирован.

Для полностью серверного запрета между физическими ПК потребовались бы разные GitHub credentials/идентичности.

## Нормальная работа

После однократной установки ничего вводить не нужно.

Просто давайте Cursor обычные задания.

## Проверить lock вручную

```powershell
.\scripts\project-lock-status.ps1
```

## Ручное получение lock

Нужно только для ручной Git-работы вне Cursor Agent:

```powershell
.\scripts\project-lock-acquire.ps1
```

## Освободить свой lock

```powershell
.\scripts\project-lock-release.ps1
```

## Аварийно снять чужой зависший lock

Только после проверки, что другой ПК реально остановлен:

```powershell
.\scripts\project-lock-release.ps1 -Force
```

Скрипт потребует ввести `RELEASE`.

## Важное ограничение Cursor Hooks

На актуальных версиях Cursor `beforeSubmitPrompt` умеет блокировать отправку промта через `continue=false`.
Это основной gate пакета.

`preToolUse` используется как дополнительная защита, а Git hooks защищают commit/push.

Не отключайте ни один из слоёв.

### Внутренний bypass pre-push

Служебные acquire/release push временно устанавливают `CURSOR_PROJECT_LOCK_INTERNAL=1`, чтобы versioned `pre-push` не заблокировал создание самого lock. Переменная устанавливается только внутри lock-скрипта и сразу восстанавливается/удаляется. Пользователь и Cursor Agent не должны устанавливать её вручную.
