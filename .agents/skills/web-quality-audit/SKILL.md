# Web Quality Audit

## Цель

Провести единый аудит сайта или страницы по пяти направлениям: работоспособность, производительность, Core Web Vitals, доступность и SEO. Навык предназначен для чистого HTML/CSS/JS и может применяться к другим стекам.

## Перед началом

1. Определи проверяемый URL, локальную страницу или набор файлов.
2. Прочитай `AGENTS.md`, `.cursor/rules/` и проектные ограничения.
3. Не изменяй код до составления списка проблем.
4. Зафиксируй тип проверки: одна страница, шаблон страниц или весь сайт.

## Порядок аудита

1. **Работоспособность**
   - страницы открываются без ошибок;
   - меню, ссылки, формы, модальные окна и кнопки работают;
   - в консоли нет необработанных ошибок;
   - отсутствуют битые изображения и запросы 404.
2. **Производительность**
   - критический путь рендеринга;
   - изображения, шрифты, CSS и JavaScript;
   - сторонние скрипты;
   - кеширование и preload/preconnect.
3. **Core Web Vitals**
   - LCP, CLS, INP;
   - причины метрик, а не только итоговые значения.
4. **Доступность**
   - семантика, клавиатура, фокус, labels, контрастность, alt.
5. **SEO**
   - индексируемость, canonical, title, description, H1–H3;
   - внутренние ссылки, sitemap, robots, JSON-LD.
6. **Безопасность и сохранность интеграций**
   - секреты не находятся во frontend-коде;
   - аналитика и формы не повреждены;
   - внешние ссылки используют безопасные атрибуты, где нужно.

## Приоритеты

- **P0** — сайт или лидогенерация не работают, утечка данных, блокировка индексации.
- **P1** — серьёзные ошибки CWV, формы, canonical, мобильная версия.
- **P2** — заметное влияние на SEO, UX или скорость.
- **P3** — улучшения и косметические замечания.

## Формат результата

Для каждой проблемы укажи:

- приоритет;
- файл, URL или селектор;
- доказательство;
- влияние;
- конкретное исправление;
- риск регрессии;
- способ проверки после исправления.

Сначала выдай аудит и план. Исправляй только после подтверждённого задания или когда пользователь прямо попросил внести изменения.
