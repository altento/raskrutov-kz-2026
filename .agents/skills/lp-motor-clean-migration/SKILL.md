# LP Motor Clean Migration — чистый перенос без мусора конструктора

## Назначение

Перенести страницу или сайт из LP Motor/Мотор в текущий проект как независимую,
семантическую и производительную реализацию на чистом HTML, CSS и JavaScript.

Исходная страница — эталон:

- внешнего вида;
- контента;
- структуры видимых секций;
- изображений и шрифтов;
- ссылок;
- адаптивного поведения;
- реально используемой функциональности.

Исходный HTML, DOM, CSS/JS-бандлы и runtime конструктора **не являются**
архитектурным образцом.

Главный принцип:

> Это реконструкция по визуальному и функциональному результату, а не
> зеркалирование, скачивание или очистка исходного DOM.

## Входные данные

Перед запуском зафиксируй:

```text
SOURCE_URL = полный URL исходной страницы
TARGET_ROUTE = целевой путь в проекте
REFERENCE_VIEWPORTS = 1440 px desktop, 390 px mobile
```

Дополнительные источники:

- локальная действующая версия;
- скриншоты;
- SEO-карта;
- тексты и ассеты;
- правила `AGENTS.md`;
- `.cursor/rules`;
- навык `forms-standard`;
- существующие общие компоненты проекта.

Если данных не хватает, используй доступные источники без выдумывания контента.
Зафиксируй ограничение в отчёте.

## Жёсткие запреты

Запрещено:

- копировать исходный HTML целиком;
- использовать DOM конструктора как основу новой страницы;
- использовать wget, HTTrack, «Сохранить страницу» или рекурсивное зеркалирование;
- создавать `mirror_site.py`, `fix_remaining_urls.py` и подобные скрипты массового копирования;
- скачивать все ресурсы домена без разбора;
- переносить `public.bundle*`, `bundle*`, `runtime*`, `vendor*`, `editor*`,
  `lpmotor*`, `motor*` и другие служебные бандлы;
- переносить стили редактора, панель управления, preview/runtime-код;
- переносить случайные ID, хэш-классы и бессмысленные wrapper-элементы;
- переносить скрытые полные дубли секций для desktop/mobile;
- механически копировать inline CSS/JS;
- переносить неиспользуемые библиотеки, полифилы и обработчики;
- копировать service worker, source maps и manifest конструктора без доказанной необходимости;
- копировать счётчики, пиксели, cookie-скрипты и формы конструктора вслепую;
- оставлять зависимость от `SOURCE_URL` или CDN конструктора;
- вставлять исходную страницу через iframe;
- использовать большие изображения через base64/data URI;
- создавать случайные заглушки, когда доступен реальный ресурс;
- выполнять самостоятельный редизайн и переписывать тексты;
- удалять сомнительные старые файлы автоматически;
- менять другие страницы;
- перезаписывать рабочие общие компоненты без необходимости;
- менять `.htaccess`, redirects, robots или sitemap без прямой необходимости;
- выполнять commit, push или публикацию без отдельной команды.

## Приоритеты

1. Сохранность текущего проекта и пользовательских изменений.
2. Визуальное соответствие.
3. Полнота контента и функций.
4. Сохранение SEO, форм и аналитики.
5. Чистота и поддерживаемость.
6. Производительность и доступность.

## Этап 1. Аудит до изменений

1. Выполни `git status`.
2. Не откатывай и не изменяй несвязанные пользовательские правки.
3. Изучи:
   - `AGENTS.md`;
   - `.cursor/rules`;
   - структуру проекта;
   - header/footer;
   - CSS-переменные;
   - общие компоненты;
   - пути и маршруты;
   - общие скрипты;
   - формы и обработчики;
   - аналитику;
   - SEO-файлы;
   - шрифты и ассеты;
   - `.htaccess` и redirect-правила.
4. Открой исходную страницу полностью на desktop и mobile.
5. Создай полноразмерные референсные скриншоты минимум на `1440` и `390` px.
6. Составь карту всех секций:
   - номер;
   - назначение;
   - заголовок;
   - текст;
   - фон;
   - сетка;
   - изображения;
   - CTA и ссылки;
   - интерактивность;
   - desktop/mobile-поведение.
7. Составь перечень:
   - форм;
   - popup;
   - меню;
   - FAQ;
   - табов;
   - слайдеров;
   - видео;
   - аналитических событий;
   - SEO-элементов;
   - сторонних ресурсов.
8. Выдели только реально используемые ассеты.
9. Определи существующие компоненты нового проекта, которые нужно переиспользовать.
10. Определи все риски потери URL, SEO, форм, аналитики и адаптива.

Перед реализацией кратко покажи:

- структуру будущей страницы;
- переиспользуемые компоненты;
- нужные ассеты;
- создаваемые/изменяемые файлы;
- обнаруженные риски.

После аудита продолжай самостоятельно.

## Этап 2. Безопасная стратегия переноса

### Для новой внутренней страницы

Создавай страницу сразу по `TARGET_ROUTE`, но не затрагивай другие маршруты.

### Для действующей главной или критической страницы

Сначала создай изолированную тестовую версию, например:

```text
index-clean.html
assets/css/home-clean.css
assets/js/home-clean.js
```

Требования:

- действующая `index.html` не изменяется;
- стили и JS изолированы;
- новая версия открывается независимо;
- общие файлы не меняются так, чтобы затронуть рабочие страницы;
- замена действующей страницы выполняется только после ручного утверждения.

## Этап 3. HTML с нуля

1. Напиши новую семантическую разметку вручную.
2. Используй элементы по назначению:
   `header`, `nav`, `main`, `section`, `article`, `footer`, `picture`, `form`,
   `button`, `a`.
3. Сохрани один H1 и логичную H2–H3-иерархию.
4. Не используй `div` вместо видимого заголовка.
5. Используй одну адаптивную DOM-структуру.
6. Не создавай полные дубли одинакового контента для ПК и мобильных.
7. Не удаляй видимый SEO-контент ради уменьшения DOM.
8. Не добавляй лишние обёртки.
9. Используй понятные классы в стиле проекта.
10. Сохрани все тексты, числа, телефоны, адреса и факты без выдумок.
11. Сохрани доступные названия, alt и aria-атрибуты.
12. Используй `a` для переходов и `button` для действий.

Ориентиры, а не формальные лимиты:

- глубина DOM по возможности до `15–20` уровней;
- отсутствие тысяч служебных элементов;
- каждый элемент имеет роль в семантике, сетке, стиле или функциональности.

## Этап 4. CSS

1. Сначала переиспользуй дизайн-токены и общие компоненты проекта.
2. Добавляй только стили новой страницы.
3. Не импортируй CSS конструктора.
4. Не копируй огромные блоки из DevTools без разбора.
5. Удали пустые media queries, дубли и неиспользуемые правила.
6. Не применяй `!important` без документированной необходимости.
7. Не используй `transition: all`.
8. Анимируй преимущественно `transform` и `opacity`.
9. Добавь `prefers-reduced-motion`.
10. Используй Grid/Flexbox и осмысленные breakpoints.
11. Не строй всю страницу абсолютным позиционированием.
12. Не добавляй глобальный `white-space: nowrap`, вызывающий overflow.
13. Сохрани размеры, отступы, цвета, сетки, фоны, тени и переносы текста.
14. Не объединяй визуально разные секции в один шаблон, если это меняет эталон.
15. Обеспечь видимые focus-состояния.
16. Изолируй page-specific CSS от других страниц.

## Этап 5. JavaScript

1. Используй vanilla JavaScript ES6+.
2. Реализуй только фактически присутствующие функции.
3. Не подключай библиотеку ради одной небольшой функции.
4. Подключай JS через `defer` или `type="module"`.
5. Инициализируй код только при наличии элемента.
6. Не создавай обработчики для отсутствующих блоков.
7. Не допускай повторной инициализации.
8. Поддержи:
   - `aria-expanded`;
   - `aria-controls`;
   - Escape;
   - управление и возврат фокуса;
   - клавиатурную навигацию.
9. Не создавай второй обработчик формы.
10. Для форм обязательно примени `forms-standard`.
11. Не переносить код отправки из LP Motor.

Допустимые функции по факту наличия:

- мобильное меню;
- popup;
- FAQ/accordion;
- tabs;
- slider;
- маска и валидация;
- lazy YouTube preview;
- другие реально используемые компоненты.

## Этап 6. Ассеты

Скачивай локально только реально используемые:

- изображения;
- SVG;
- фоновые изображения;
- иконки;
- необходимые шрифты.

Не скачивай:

- скрытые ресурсы;
- дубли размеров без пользы;
- editor icons;
- tracking pixels;
- source maps;
- ресурсы других страниц;
- код конструктора.

Требования:

1. Размещай файлы по принятой структуре проекта.
2. Давай понятные имена, если это безопасно.
3. Не перезаписывай оригинальные ассеты при оптимизации.
4. Удаляй EXIF и лишние метаданные.
5. Используй WebP, а AVIF — при практической пользе и fallback.
6. Применяй `picture`, `srcset`, `sizes`.
7. Не отправляй изображение 1920 px в карточку 300–500 px.
8. Для `img` задавай `width`/`height` или стабильный `aspect-ratio`.
9. LCP-изображение:
   - не lazy;
   - `fetchpriority="high"` только при подтверждённом LCP;
   - preload только одного реального LCP-ресурса;
   - обнаруживается из HTML.
10. Ниже первого экрана — `loading="lazy"` и `decoding="async"`, если это не
    ломает слайдер.
11. Контентные изображения имеют точный alt, декоративные — `alt=""`.
12. Не оставляй `src=""`, пустой `srcset`, `url()` или ссылки на исходный домен.

## Этап 7. Шрифты и предотвращение CLS

1. Подключай только реально используемые начертания.
2. Предпочитай WOFF2.
3. Используй `font-display: swap` или обоснованную альтернативу.
4. Не подключай один шрифт несколькими способами.
5. Preload только для шрифтов, нужных первому экрану.
6. При заметном скачке метрик настрой fallback-метрики (`size-adjust`,
   `ascent-override`, `descent-override`, `line-gap-override`) после измерений.
7. Заранее резервируй размеры изображений, видео, форм, popup и динамических блоков.
8. Не вставляй контент над уже показанным первым экраном после загрузки.

## Этап 8. Контент, ссылки и маршруты

1. Перенеси весь видимый контент.
2. Не сокращай и не переписывай его самовольно.
3. Сохрани порядок секций.
4. Сохрани действующие внутренние URL.
5. Сохрани `tel:` и WhatsApp.
6. Не оставляй технический домен или URL конструктора.
7. Не меняй утверждённый `TARGET_ROUTE`.
8. Если URL старой и новой страницы различаются, не создавай redirect
   предположительно: зафиксируй необходимость и текущие правила проекта.

## Этап 9. SEO, AEO и микроразметка

Сохрани или корректно перенеси:

- `<html lang>`;
- Title;
- Description;
- canonical на боевой домен;
- robots meta;
- Open Graph;
- hreflang, если есть;
- favicon;
- один H1;
- H2–H3;
- индексируемый текст;
- внутренние ссылки;
- JSON-LD;
- `Organization`/`LocalBusiness`;
- `WebSite`;
- `BreadcrumbList`;
- `FAQPage`;
- другую реально используемую микроразметку.

Не копируй дублирующую и ошибочную разметку конструктора. Сохрани смысл и
валидность. Ошибку сначала зафиксируй; не меняй SEO-смысл без необходимости.

Не изменяй автоматически:

- `robots.txt`;
- `sitemap.xml`;
- canonical других страниц;
- глобальные redirect-правила.

## Этап 10. Формы и интеграции

1. Не переноси формы, endpoint, токены и скрытую инфраструктуру LP Motor.
2. Воспроизведи внешний вид формы.
3. Подключи её к существующему механизму нового проекта.
4. Примени навык `forms-standard`.
5. Сохрани:
   - `name`;
   - обязательность;
   - маску;
   - consent;
   - success/error;
   - страницу и форму;
   - UTM;
   - события аналитики.
6. Не выполняй реальную тестовую отправку без разрешения.
7. Не имитируй успех, если внешняя интеграция недоступна.

## Этап 11. Аналитика и внешние скрипты

1. Сохрани рабочую аналитику нового проекта.
2. Не копируй счётчики конструктора автоматически.
3. Не дублируй Яндекс Метрику, GA4, Google Ads или GTM.
4. Не меняй идентификаторы.
5. Сохрани действующие события кликов, форм и CTA.
6. Не отправляй тестовые конверсии без разрешения.
7. Не удаляй тяжёлый виджет молча: зафиксируй безопасную альтернативу в отчёте.

## Этап 12. Адаптив и визуальное соответствие

Проверь минимум:

- `1920`;
- `1440`;
- `1280`;
- `1024`;
- `768`;
- `390`;
- `360` px.

Для каждой ширины проверь:

- порядок секций;
- контейнеры;
- высоты;
- сетки;
- количество карточек;
- переносы заголовков;
- отступы;
- фоны;
- кадрирование изображений;
- кнопки;
- меню;
- формы;
- FAQ/tabs/sliders;
- отсутствие наложений;
- отсутствие обрезанного текста;
- отсутствие горизонтального скролла.

Сделай full-page screenshots на `1440` и `390` и сравни секция за секцией.
При доступности используй overlay/pixel diff.

Страница не готова только потому, что в ней есть все тексты.

## Этап 13. Производительность

Технические цели, не являющиеся разрешением ломать дизайн или функциональность:

- нет зависимости от исходного домена;
- нет бандлов конструктора;
- нет 404/403;
- нет ошибок приложения в консоли;
- нет пустых `img`/`iframe`;
- нет desktop/mobile дублей;
- минимальный JavaScript;
- WOFF2 и `font-display`;
- LCP ≤ `2.5 s`;
- CLS ≤ `0.05` как желаемый уровень и не выше `0.1`;
- TBT ≤ `100 ms` как цель;
- PageSpeed mobile `90+` как цель, а не выдуманный результат.

Не заявляй достижение по одному прогону. Если Lighthouse доступен, сделай три
прогона desktop и mobile и используй медиану.

## Этап 14. Обязательные проверки

1. Запусти сайт существующим способом.
2. Проверь Network:
   - нет 404/403;
   - нет запросов к `SOURCE_URL`;
   - нет CDN/runtime конструктора;
   - нет дублирующихся загрузок.
3. Выполни поиск по проекту:
   - исходный домен;
   - `public.bundle`;
   - `lpmotor`;
   - `motor`;
   - `editor`;
   - `runtime`;
   - `vendor`;
   - `src=""`;
   - пустой `url()`;
   - `http://`.
4. Каждое совпадение проверяй по контексту, не удаляй легитимный текст по слову.
5. Проверь:
   - header/menu;
   - все ссылки и CTA;
   - FAQ;
   - формы;
   - popup;
   - tabs/sliders;
   - телефон и WhatsApp;
   - аналитику;
   - JSON-LD;
   - клавиатурную навигацию.
6. Проверь HTML и JSON-LD валидаторами, если доступны.
7. Проверь console.
8. Выполни `git diff --check`.
9. Покажи `git status`.
10. Не выполняй commit/push/publication.

## Этап 15. Кандидаты на удаление

Сформируй отдельный список:

- файл;
- откуда появился;
- найденные ссылки на него;
- влияет ли на видимую страницу;
- влияет ли на функцию;
- размер;
- уверенность удаления;
- способ проверки после удаления.

Не удаляй сомнительные файлы автоматически. Список — для ручного решения.

## Финальный отчёт

Покажи:

1. созданные и изменённые файлы;
2. переиспользованные компоненты;
3. скачанные и оптимизированные ассеты;
4. что намеренно не перенесено как мусор;
5. результаты проверки ссылок, console, HTML и JSON-LD;
6. таблицу Lighthouse:
   - Performance;
   - FCP;
   - LCP;
   - Speed Index;
   - TBT;
   - CLS;
   - общий вес;
   - запросы;
   - CSS;
   - JS;
   - DOM-элементы;
7. пути к desktop/mobile screenshots;
8. оставшиеся визуальные отличия;
9. внешние интеграции, которые нельзя проверить;
10. список кандидатов на удаление;
11. риски перед заменой действующей страницы;
12. чёткий вывод: готова ли страница к ручной проверке владельцем.

Не заявляй «1:1», «всё работает» или «90+», если это не подтверждено
фактическими проверками.

## Критерии готовности

Перенос готов только когда:

- страница визуально близка на desktop и mobile;
- весь видимый контент перенесён без выдумок;
- реально нужная интерактивность работает;
- необходимые ресурсы локальны;
- нет зависимости от конструктора;
- нет его DOM/CSS/JS-бандлов;
- нет битых файлов и новых ошибок console;
- сохранены URL, SEO, микроразметка, формы и аналитика;
- адаптив проверен на контрольных ширинах;
- производительность измерена честно;
- действующая критическая страница не заменена без утверждения;
- нет commit, push и публикации без отдельной команды.
